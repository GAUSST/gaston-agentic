# Gaston Agentic — v1.5.5

Gaston is a **project-agnostic** engineering tool. It discovers the current
project's stack, routes, tests, workflow, and conventions; no application name
or project-specific paths are baked into Gaston. Its engineering standard is
**production-quality code and deep architectural reasoning**, not the shortest
implementation: explicit system boundaries, invariants, tradeoffs, failure modes,
contract compatibility and evidence-backed review, scaled to actual project risk.

The established command contract is unchanged: `dev init`, `dev`, `dev models`,
`dev sessions`, `dev uninstall`. v1.5.1 adds **`dev update`** and a cached,
non-blocking, at-most-daily notification on `dev` startup. Updates are never
installed automatically. The official public source repository is **GAUSST/gaston-agentic**;
`dev update` remains unconfigured until the publisher is explicitly trusted once
with `dev update --set-repo GAUSST/gaston-agentic`. See
`docs/UPDATES.md` for release, integrity, testing, and rollback details.

**Platform status:** the standard Unix `./dev` launcher works without pip,
pipx, or touching the system Python packages. The shared installed CLI is
available in code on Windows/macOS/Linux, but a native, no-Python Windows
first-run executable is not supplied and actual Windows/macOS end-to-end runtime
parity is **not yet certified**.

# Gaston Agentic

An engineering workflow with one developer-facing conversation and one delegated coding session.

- **Engineering Lead:** Your main AI conversation. Plans, delegates, reviews actual changes and checks results. Owns tests and scoped small implementation/repairs.
- **Builder:** Separate task-scoped session; focused corrections reuse it within context budget. Edits code and implements Lead-requested corrections; does not run tests.

The installer offers Codex + Claude, Codex only or Claude only. Choose a concrete model for each role; **there is no Account default model option and no hardcoded Codex model version**. For Claude, choose `claude-sonnet-5-5`, `claude-opus-5-5` or `claude-haiku-5-5`; for Codex, the installer shows the **full, exact model IDs** (such as `gpt-6-luna`), dynamically obtained from the installed CLI's model catalog, never family names alone. Recommended effort: Builder Low, Lead Medium. **Codex reasoning choices normally come from the selected model's `codex debug models` catalog entry** (Gaston permits only Low, Medium, High, Xhigh and Max, filtered by model metadata when available; None, Minimal and Ultra are excluded even when advertised). A previously saved excluded level requires reselection, not an automatic downgrade. Hidden catalog IDs with reasoning metadata can be entered directly, but are not automatically recommended. If an exact ID has no published reasoning metadata, select a candidate from those five permitted reasoning levels (not guaranteed supported by the model) and Gaston automatically runs one isolated, read-only, ephemeral Codex turn for that exact pair (this consumes model allowance). Only a completed check is recorded in the workspace configuration; a rejection returns to model selection and does not save the rejected pair. Successful direct evidence is reused for the same pair on later launches; newly published metadata takes precedence. Account access can change, and the check confirms acceptance of the request, not the provider's internal effective reasoning. Saved settings without either compatible metadata or direct-check evidence prompt reselection. If a saved reasoning level is incompatible, setup asks you to choose a supported level. Invalid numbers or exact IDs repeat the same question; only an empty answer accepts the displayed valid default. When the catalog is unavailable but Codex is installed, an exact ID can still be checked directly; if the CLI itself is unavailable and no usable evidence exists, setup stops with a clear blocker. Claude's five documented effort levels are offered, subject to the selected model's and organization's limits. Model/effort combinations are never silently downgraded by Gaston Agentic. Enter either the displayed option number or the exact model ID directly.

During **`./dev init`**, the installer automatically reuses already registered role sessions and never asks for existing session IDs; missing sessions are created by Gaston when first used. A dangling Claude binding with no local transcript is archived and recreated under the role lock; existing transcripts are retained. The installer also checks provider authentication, Codex model/effort compatibility using local CLI metadata or recorded exact-pair execution evidence, Claude effort syntax and Advisor environment conflicts. There is **no separate model-check command**. Catalog-only checks require no inference credits; an undocumented exact-pair check uses one short inference turn. Claude account entitlements and Advisor activation can only be confirmed in a real enrolled session. Failed or unexecuted checks must never be reported as passed.

**Advisor:** Whenever Claude is Engineering Lead, native Advisor `claude-opus-5-5` is the default regardless of the selected Claude model. No Advisor question appears during setup. Saved explicit Advisor IDs and `off` are preserved. Legacy unversioned Advisor aliases migrate to the new default. Change it later in the interactive `./dev models` menu. Advisor is disabled for the Builder, not for unrelated Claude chats. Advisor support and consumption are provider/account-dependent; `claude-fable-5-2` is optional and may require usage-credit consent; Gaston never enables billing. An explicit `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` in your environment is respected rather than bypassed. Actual access is verified only when the enrolled Claude session runs. If your subscription rejects the selected Advisor, change it to `off` in `./dev models`; the toolkit does not automatically accept extra charges. Only registered project sessions participate in automation.

## Install

Extract the Gaston release ZIP into your development workspace. On **Linux/macOS**, run `./dev init` once. This invokes Gaston immediately and installs a user-local `dev` command **without pip, pipx, sudo or system-Python modifications**. In future terminals, simply use `dev`. The launcher finds the workspace from your working directory; it does not bind to a hardcoded project path. If the user executable directory is not already on PATH, `./dev` adds only that directory to the current shell's startup file for future terminals; the current terminal can always use `./dev`.

**Windows:** the installed `dev` Python console-script entrypoint still requires a native Windows installation bootstrap. No `dev.cmd` is shipped. Windows first-run parity is **not yet verified**; do not mistake the Linux/macOS self-registration for a completed native Windows installer. Never use `pip --break-system-packages`.

**Resumable setup:** The read-only installation plan and `GO` confirmation still appear on **every interactive `./dev init`**. Once you approve, the wizard immediately saves your selected language, AI architecture, role models, reasoning, accepted testing-category approvals and completed setup checkpoints to `.agentic/config.json` and `.agentic/local/setup-progress.json`. If setup is interrupted or an installation fails, simply rerun `./dev init`: previously completed choices are reused, and only unfinished installation work is attempted. The installer rechecks actual tool readiness rather than assuming a saved checkpoint means an installed tool works. Existing language/AI selections are shown as saved, not asked again; the optional **“Change saved language or AI configuration?”** question defaults to No. Choose Yes when you want to reselect language, architecture, role models or reasoning. Even if you choose No, saved incompatible or missing model/effort settings are repaired interactively. Use `./dev models` to change role models, reasoning or the Advisor, even during incomplete setup, then rerun `./dev init` to finish initialization. An interrupted setup remains **not ready** until the final verification succeeds. A declined testing-category installation is not treated as approved.
 Setup prompts show the exact Enter behavior: `[default: Yes]` for essential testing categories needing setup, explicit defaults for other confirmations, `[default: claude-sonnet-5-5]` for model choices, and `[optional; Enter to skip]` for optional values. The French setup uses corresponding French labels.

## Use

There are six public commands: the five existing commands and `dev update`. The Builder and Engineering Lead invoke tools,
MCPs and verification internally; the developer does not run test or handoff subcommands.


```bash
dev             # Engineering Lead
dev sessions    # Agent connections and recent activity
dev models      # Choose models, reasoning and Claude Lead Advisor
dev init        # Finish or revisit setup
dev uninstall   # Preview and remove Gaston Agentic
dev update      # Check and install a user-approved signed release
```

All commands except init and uninstall require completed setup; `uninstall` works even when setup is incomplete.

Describe a feature, issue, screenshot or policy to the Engineering Lead. When substantial implementation is ready after preflight, the Lead invokes the private `gaston_verify.delegate_to_builder` tool for a bounded slice; the task-scoped Builder processes the task while the Lead chat stays open. The Lead inspects the actual changes and test evidence from `delegation_status` and its read-only tools before accepting. Session-end hooks remain optional compatibility helpers, not the core handoff. After accepted work, the Lead removes only its own temporary handoff documents when safe; permanent specifications and verification evidence are retained. The developer need not reauthorize this narrowly scoped cleanup.

The setup and role-local launch expose verification MCP tools to the selected Engineering Lead (Claude or Codex), never the Builder; it can install Playwright Test as a separate CLI runner in an isolated local sandbox. Codex-only mode passes a role-scoped MCP override to the Lead command, without registering a user-wide server. During `./dev init`, there is at most **one [default: Yes] approval per incomplete testing category** (Backend testing when a Java project exists, Mobile testing, and Web E2E). A fully configured category is silently reused and setup moves to the next one; no category prompts run in non-interactive mode. One approval covers the category’s project-local setup actions, including downloads and role-scoped MCP registration. Host package installation and starting Docker require a separate interactive confirmation showing the commands, both with `[default: Yes]`; PostgreSQL smoke verification is also offered separately with `[default: Yes]`. Press Enter to accept the displayed default or answer No to skip. Non-interactive setup never runs host installation or Docker startup. Declining skips that category, leaving incomplete coverage visible in the setup report. Gaston targets Windows, macOS and Linux natively. Setup offers known distribution packages for missing host tools (Git, JDK, curl, psql, Maven/Gradle, Node/npm, Docker Engine on Ubuntu, and separately approved Docker Desktop on macOS). Existing Debian/Fedora/WSL compatibility is retained on a best-effort basis. No administrator command runs without fresh approval in a real interactive terminal. Existing tools are reused; versions are rechecked, and unsupported platforms, distro packages that do not meet required versions, Docker socket access, PATH or SDK issues remain visible with manual guidance. No automatic group/permission changes or application dependency changes. Browser MCP is for interactive navigation in the Lead session and Playwright Test is for repeatable browser/API checks. The Lead can use browser MCP; the Lead authors tests and handles scoped small fixes via tools. Use only authorized local or sandbox test environments; browser actions can change data in the visited web app. Neither replaces Maestro native mobile E2E, nor generates application tests by itself. See `docs/BACKEND_VERIFICATION.md` for strengthening Java/PostgreSQL/API testing.

**Operating systems:** Gaston now ships a common Python `dev` console-script entrypoint targeting native Windows (PowerShell or CMD), macOS and Linux. Install it once using `./dev` for the first local Unix launch (which registers the normal `dev` launcher), then use `dev init` and `dev` on every host. The prior Windows preview and `dev.cmd` are retired. Platform-specific kernel locking, private Windows ACLs and process handling use shared platform helpers; Windows/macOS additionally require `psutil` (pip installs it). Real Windows/macOS CI and provider/browser/database smoke tests are still required before platform parity can be claimed. The optional Unix checkout `./dev` remains. See `.agentic/LAUNCHER.md`.

**Terminal setup interface:** The wizard uses a restrained, professional color palette on compatible terminals: blue for steps/active operations, green for success, amber for attention, red for failures, and muted grey for informational or skipped items. `NO_COLOR`, `CLICOLOR=0`, `TERM=dumb`, or redirected output disables ANSI styling automatically. The five steps, explicit defaults, `GO` confirmation, and resumable configuration are unchanged. Step 4 displays a compact snapshot of detected applications and runnable test checks—not test results. Step 5 simply reports `Setup complete.` and `Run ./dev to start.` when ready. The internal JSON setup report is still written but its path is not printed to the user.

**Automatic project discovery:** After initial setup, Gaston rescans the workspace at the start of agent work and after Builder changes. Java/Spring Boot, Flutter and web repositories added later are recognized without rerunning `./dev init`. Relevant Maven/Gradle, Flutter analyze/unit/widget and Playwright E2E gates are refreshed when real project files/tests exist; app-specific missing dependencies or test suites are reported as blocked and the Lead configures them using scoped tools, rather than being marked as passed. The installer’s Step 4 shows a snapshot of **current testing readiness**, not a permanent list of registered checks. Test detection does not silently install dependencies.

**Smart verification:** The Lead picks meaningful backend/API/DB/security checks according to the task and changed code, and checks dependent Flutter/browser sections when an interface or shared behavior can affect them. Existing tests are reused, duplicate commands are executed only once, and the selected checks and blockers are saved in each task's `verification_plan.json`. The Lead can create small `curl` JSON test cases from actual endpoints; these execute against a **running loopback test API only** using `AGENTIC_TEST_API_BASE_URL`. Missing required checks are reported as blocked, never passed. No extra setup prompts or commands are added. See `docs/BACKEND_VERIFICATION.md`.

**Evidence and context efficiency:** The verifier retains complete Maven/Gradle stdout/stderr in private `.agentic/local/backend-logs/` files and returns compact status, test summaries, timing, paths and evidence IDs to the Lead. When investigating failures, call `acceptance_evidence_detail` for a specific task/check ID; log excerpts are only returned on request. A planned slice with changed, existing JUnit test classes automatically runs those classes (up to eight); when no reliable selector exists, the full backend gate remains required. Passing backend evidence may be reused across tasks only within 30 minutes when the complete Git workspace fingerprint, project, selector and toolchain/test environment match, with source provenance recorded and failed or borrowed evidence excluded. Integrated checkpoint backend acceptance and managed live API checks always run fresh; any revision/environment change or explicit `force=true` triggers a rerun. Tool metadata (timing and result byte length, never prompts, credentials, or logs) is recorded privately in `.agentic/local/mcp-tool-usage.jsonl` for future performance measurement. The existing safe Lead rollover remains enabled because it reduces context peaks; it is not a substitute for reducing unnecessary calls.

**Database diagnostics:** PostgreSQL testing uses real isolated project fixtures; pgAdmin is not required. The Lead can use `workspace_database` with host `psql` for authorized local metadata, indexes, constraints, statistics and opted-in synthetic counts/duplicate checks/record samples. The setup wizard installs only the PostgreSQL client, not a host server. With approval, it starts an isolated `docker.io/library/postgres:16` smoke container (no exposed ports, application data or host bind mounts), executes `SELECT 1`, and confirms its removal. Successful smoke evidence is reused only for the same Docker daemon and image ID; it does not establish application-specific Testcontainers, migrations or business correctness. Short-lived fixtures must assert persisted effects before teardown; a tool discovery result is not a database test. When backend readiness is verified, interactive init also offers an independent workspace-owned persistent PostgreSQL 16 development database (default Yes). Its named volume is never automatically removed; it publishes only on 127.0.0.1 with a Docker-selected port. Setup prints the connection details and location of private credentials; pgAdmin can connect manually. Interactive backend setup also offers optional desktop pgAdmin after database checks, even if the persistent database was skipped. The prompt defaults to No, existing installations are reused, and absence does not block setup. Ubuntu uses `pgadmin4-desktop` from APT; on supported x86_64 Ubuntu releases the prompt explicitly displays the official vendor repository and scoped signing-key paths if these need to be added. macOS uses the Homebrew `pgadmin4` cask; Windows uses `PostgreSQL.pgAdmin` from WinGet. Unsupported package/repository configurations receive official manual guidance. No pgAdmin server registration or credential import is automatic. The application is not automatically configured or migrated. Gaston uses a distinct read-only account for metadata; fixture data still requires opt-in. Automated tests remain disposable. Uninstall leaves the development container, volume and credentials intact. See `docs/LEAD_WORKSPACE_OPERATIONS.md`.

Tests must run before they can be reported as passed. Missing database, device or E2E evidence is reported as unverified. Production deployment and payment-sensitive changes require explicit human approval.

## Upgrade (keep your work)

Close every Lead (including old/forked conversations), cancel any legacy native quota schedules and wait for any active Builder to finish. Back up `.agentic/config.json`, `.agentic/local/`, task evidence and locally evolved toolkit files. Extract the complete ZIP at the project root, overlay only shipped files (never use `rsync --delete`), then restart `./dev`. No uninstall or session recreation is needed. Retired exact shipped files are cleaned at idle startup; modified copies are preserved. Run `./dev init` if you want to enable optional Serena or revisit setup choices. Ask the Lead for a new `environment_status` call: the returned toolkit release, build and server path identify the loaded process. The manifest is the canonical release identifier.

## Engineering workflow

The shared role and acceptance contract is in `AGENTS.md`; Claude imports it from `CLAUDE.md`. The Lead decomposes large work into monitored slices, handles inspections and test setup in parallel with substantial Builder implementation, takes over repeated defects after two unsuccessful correction rounds, and independently reviews the final integrated results. Code and documentation review are bound to current task evidence; readability, difficult-logic comments and dead-code investigation are part of acceptance. Use exact requirements and current repository evidence; no fabricated success. See `docs/VERIFICATION.md` and `docs/BACKEND_VERIFICATION.md` for live verification.

The toolkit collects local evidence and usage, learns verified lessons, scans for maintainability candidates and can stage, test, activate or roll back toolkit-only improvements at a safe startup boundary. Security-sensitive changes require explicit approval; recovery code and baseline tests are protected. No automatic model switching or updates: only an optional cached release notification is shown. Updates require an explicit `dev update` command and approval. Project learning stays local. Export the reviewed manifest-owned toolkit only when requested. Whole-package audit and compatibility checks apply to evolution candidates as well as distributable releases. Existing source files can be changed with hash-validated unique text replacements instead of full-file submissions. Idle maintenance removes failed or obsolete candidate snapshots without discarding evidence or applied rollback history.

## Native sessions and testing

Claude Lead is a native interactive conversation; existing registered IDs are preserved until a safe checkpoint rollover; newly created sessions receive readable names. `./dev sessions` displays the ID. Do not resume a session concurrently with a managed Lead. Codex-only uses role-local MCP overrides, not global registration. Hook trust is approved in the provider's own UI; never forge trust. Backend, mobile and Web E2E setup categories reuse existing tools and use one approval per incomplete category plus separate consent for host installations and disposable PostgreSQL smoke testing. Setup does not start emulators. Existing uncommitted application changes do not block normal development; review overlaps and preserve unrelated work.

## Uninstall

`./dev uninstall` previews the manifest-owned toolkit removal and offers **keep** (default) or **erase**. **Keep** removes Gaston code while preserving `.agentic/local`, task history, run evidence, custom rules, configuration and verified provider sessions, so a later `dev init` can reuse existing context. **Erase** additionally deletes Gaston-owned workspace state and exactly verified provider transcripts; it requires the separate phrase `ERASE GASTON DATA` and then `UNINSTALL`. Existing application source and user-owned documents are untouched in both modes. Modified shared toolkit files require separate approval. Unknown or unrelated provider sessions and global tools are never deleted. Close managed sessions before uninstalling. Do not uninstall merely to upgrade.

**Planned v1.6 core separation:** the current v1.5 toolkit still stores runtime code inside each workspace. Central installation of the engine, migration to `.gaston/` integration-only project metadata, and explicit project-level reinitialization require a separate tested migration; this uninstall change only establishes the safe preservation contract and does not claim the new runtime layout already exists.

Automated toolkit tests do not prove actual authenticated provider, device or application behavior. Inspect real local results before release.

## Native interruption recovery

Gaston reconciles stale managed session locks and matching activity markers before opening a chat. It checks PID birth identity on Linux and preserves genuinely live or uncertain provider processes. Unfinished jobs with a proven-dead worker are persisted as blocked/resumable; an existing completion wait automatically retries a proven pre-provider lease refusal at most once per revision. For other interruptions, the Lead uses `resume_builder` to continue the same task/revision, not a new delegation. Recovery does not terminate discovered processes or restart cancelled work. A gracefully interrupted worker stops its own isolated provider process group; hard-killed workers with live or unverifiable provider children remain protected. The fallback feedback worker uses a crash-releasing kernel lease; interrupted feedback is quarantined rather than replayed. `runtime_recovery_status` reports interrupted jobs and deduplicated internal-exception incidents. An active Lead investigates and links a candidate to an incident via `stage_evolution`; candidates still require regression, compatibility and safe activation. No autonomous extra model request is made.

A workspace-wide Lead lease prevents simultaneous managed Leads across providers; new verifier instances check the lease and parent process, and reject release changes. Linux and macOS process detection also checks for identifiable unmanaged native sessions; an old already-loaded server cannot be retroactively patched, so close it before upgrading. With explicit developer consent, quota recovery schedules one local Builder-only wakeup, not a new Lead. Keep the host and wakeup process running; an interrupted scheduler or release upgrade may require manual resumption.

## Context efficiency and optional Serena

Builder sessions rotate per independent task (or before a correction when the last measured context is at least 120k tokens), retaining all prior provider transcripts. A fresh Builder gets original task/spec snapshots, code state and previous correction evidence. The Lead remains one interactive conversation; checkpoints can compact or safely rotate an oversized Lead session at the next idle launch, never while a task or approved recovery is active or newer user messages are present. Durable project context and exact task/plan records remain available.

During interactive `./dev init`, Gaston detects an existing compatible Serena CLI or offers a workspace-local installation using uv (Python 3.13); skipping is valid. The provider launches a private stdio semantic MCP proxy with the current workspace, no dashboard, no memory tools and no edit/project-switching tools. No global MCP registration. Existing native tools are the fallback. Source navigation must name a workspace-relative source path; source edits remain in the existing scoped engineering workflow. Serena may create its own project/index files; its language-server availability depends on the installed stack.

The audit counters are available through task metrics and learning reports. Historical ambiguous CLI lifetime counts are retained for diagnosis, not included in verified task totals. Native Codex/Claude transcripts are inspected locally for counter differences; missing usage is unknown. A measured reduction in gross input is not automatically a reduction in subscription quota. The next real provider run is necessary to measure the effect.

Quota recovery requires the developer’s explicit decision for each interruption. Gaston schedules a single local Builder-only wakeup after consent and a verified timezone-aware retry time; it validates the existing task, attempt identity and recovery token before resuming. It never launches a second Lead or a provider-native scheduled conversation. The host and wakeup worker must remain running; interrupted recovery may require manual resumption.


## Engineering efficiency
**Project continuity:** Gaston prescribes no plan filename, milestone numbering or planning method; optional domain packs are disabled by default on fresh installation. Existing project files can be approved as context sources with `register_project_context_sources` (workspace-relative paths; no content copied or edited). A private registry lives in `.agentic/local/`; the optional structured `record_project_roadmap` remains supported for prior users. On Lead startup or native compaction, Gaston reintroduces the approved files and points to the originals for full reading. A legacy verified source can be recovered by matching the SHA256 saved in an older Lead checkpoint. If no source is approved, Gaston suggests potential files but never declares them authoritative. A developer may explicitly register an empty source list when their workflow has no external plan; rotation will then rely on the preserved factual checkpoint and task records. Automatic Lead rotation requires a saved checkpoint and matching context fingerprints; changed, missing or unapproved sources block rotation. None of the developer's documents, configs, sessions or context registries are packaged in releases.

The Lead context budget is sampled automatically at completed slice/checkpoint boundaries and a bounded Claude Stop-hook probe. A factual user-intent checkpoint is still required for safe rollover; Gaston never kills a native conversation or starts a duplicate Lead. Codex Lead uses the MCP boundary advisory. Close/reopen `./dev` for an eligible rollover.

The Lead should run `prepare_builder_dependencies` **before the first Java delegation or when build dependencies change**. It compiles the trusted project baseline offline using the same workspace-local dependency cache, and reports exact blockers before paying for a Builder task. If offline dependencies are unavailable, the Lead must ask for project-specific approval to allow a single online fallback. The preflight is not acceptance; a Builder may still have sandbox restrictions, and must compile its own final changes. Java Builders run `python3 .agentic/builder_compile.py <project>` inside the delegated sandbox. Compilation is offline-first, compile-only, prefers the executable project `./mvnw`, and uses the isolated `.agentic/local/backend-dependencies` cache. If the offline attempt is blocked specifically by missing dependencies or an uncached Maven Wrapper distribution, the helper reports that online resolution is needed without allowing an implicit wrapper download. Only after explicit developer approval may the Lead authorize one retry with `--allow-network`; the helper still tries offline first and never retries cache-permission or source compilation failures. Provider sandbox network restrictions and configured repository access still apply. A successful compile produces a fresh attempt-bound receipt, not a test pass; the Lead independently verifies. A cold cache or sandbox restriction is reported accurately.

The Lead can batch multiple exact replacements in a single file using `lead_edit_files`: repeat the path and original SHA256 for each non-overlapping old/new text pair. All snippets refer to the original file. Full-content writes stand alone per path; all groups are validated before writes and each file is replaced atomically.

Additional exact delegation paths update the plan scope. Idle tasks can request scoped extensions, record inspected answers to pending questions, or abandon an empty Lead micro-task without fabricated edits. Reconcile unexplained scope observations with explicit attribution evidence; extend scope first for legitimate Builder changes. Prior records remain auditable. Known direct native edits are scoped where hooks are active; arbitrary shell and external tools are not path-sandboxed. Serena remains optional and records retrieval counts, outcomes and returned bytes.

The Lead may declare ordinary non-executable prose paths before verification. Reuse requires matching runtime revision and Git workspace fingerprints; contracts, executable files, other gates and documentation coverage are not skipped. No measured savings are claimed until comparable real workloads are observed.

## Central-engine migration: staged implementation

The globally installed `dev` Python distribution now also **packages Gaston's engine** as `gaston_engine`, not just the CLI wrapper. This is a backwards-compatible step towards v1.6. **The current CLI still dispatches to each legacy workspace's `.agentic` files; global dispatch is not active yet. Do not remove or move `.agentic`.**

The target is one independently updated engine and only project-specific configuration, product context, sessions, tasks and evidence inside the application. Future `dev init` and `dev uninstall` will use this separation, retaining context by default. See [central-engine migration](docs/CENTRAL_ENGINE_MIGRATION.md). No automatic migration, file deletion, or new project initialization happens in this packaging phase.
